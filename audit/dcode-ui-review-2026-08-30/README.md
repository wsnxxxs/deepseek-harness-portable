# DCode UI 对 DSH 官方 WebUI 的产品审计

日期：2026-08-30

## 结论

DCode 已经不是简单换皮：它在 Git、Diff、目标/计划、命令输出、插件市场、学习资料库、使用统计、命令面板、消息导航、反馈与分支等方面形成了明显的工作台优势。当前最重要的方向不是继续增加常驻面板，而是把这些能力收束成一个“随任务展开的开发驾驶舱”。

现阶段 DCode 在开发能力和视觉完成度上已领先官方界面，但在首次可用性、状态可信度、复杂信息的收纳，以及当前会话页稳定性上仍落后。先修复可信度与稳定性，再做渐进披露和高频任务闭环，才有机会从“功能更多”升级成“体验全面更好”。

## 审核范围与证据

- 审核当前工作区源码与当前构建，而非仅看历史文档。
- 在同一 Runtime、同一工作区和同一会话状态下切换 DCode 与官方界面比较。
- 主视口为 1440 × 960，并补充 900 × 900 的窄桌面检查。
- 执行 `pnpm run dcode:test`：122 项全部通过；当前运行时仍暴露了测试未覆盖的 React 重渲染错误。
- 没有可用的 DeepSeek API Key，因此没有执行真实模型回复、长对话、工具链和反馈提交的完整端到端流程。

## 直接对比

| 维度 | DCode 当前状态 | 官方 WebUI | 判断 |
| --- | --- | --- | --- |
| 开发工作流 | Git/Diff/提交入口、目标、计划、命令输出、详情联动 | 以会话和工具详情为主 | DCode 明显领先 |
| 高手效率 | 命令面板统一搜索任务、文件和操作；支持快捷键 | 路径更简单，但跨功能跳转较弱 | DCode 领先 |
| 首次使用 | 空状态简洁，但无 API/模型就绪指引，禁用态原因弱 | 有明确 API Key 引导，但重复弹窗打断 | 官方当前更可靠；DCode 可做出更好的非阻塞版本 |
| 模型选择 | 菜单紧凑、推理强度分层清楚 | 简单直接 | DCode 略领先，但缺能力、上下文、视觉、费用和可用状态 |
| 插件能力 | 市场、安装审阅、更新、管理、配置齐全 | 主要依赖底层插件能力 | DCode 功能领先，但目录质量和信息架构是高风险项 |
| 视觉 | 统一的深色工作台语言，细节较完整 | 更克制、更干净、品牌锚点更强 | DCode 完成度领先，官方在留白和聚焦上更稳 |
| 大规模信息 | Git 290 项、运行时插件 179 项时过密 | 能力较少，因此更简单 | DCode 落后，需要分层、搜索和虚拟化 |
| 可访问性 | 多数菜单/对话框角色正确；设置标题、插件名称、补全控件仍有语义问题 | 本次未做完整辅助技术对比 | DCode 需要专项收尾 |

## 关键流程审计

1. **首次进入 — 需改进**

   DCode 空状态视觉干净，但无工作区、无会话或缺少 API Key 时，用户只看到禁用的输入区，缺少“下一步做什么”的明确就绪清单。官方的阻塞式弹窗过重，但它至少说明了缺失项。

   证据：[DCode 空状态](01-dcode-start.png)、[官方 API 引导](03-official-api-onboarding.png)、[官方同工作区空会话](18-official-same-workspace.png)

2. **打开工作区与开始任务 — 强**

   DCode 能在左栏、顶部、输入区和右侧状态区同步同一工作区/会话，且与官方界面共享真实状态。900px 宽度下会自动收起右栏，基本布局退化合理。

   问题是工作区名称在顶部和输入区重复；空白任务默认打开右侧预览也浪费宽度。应明确“顶部是全局范围、输入区是本次覆盖”，否则只保留一个入口。

   证据：[DCode 工作区](05-dcode-workspace.png)、[窄桌面](16-dcode-narrow.png)

3. **输入与模型选择 — 良好**

   支持 `/` 指令、`@` 文件/技能/命令、拖放和粘贴图片、权限模式、模型和推理强度；这是超过官方的扎实基础。模型菜单本身清楚，但只显示名称，无法帮助用户判断能力、视觉支持、上下文窗口、速度/费用、实验状态和凭据是否就绪。

   证据：[模型一级菜单](06-dcode-model-menu.png)、[模型列表](07-dcode-model-list.png)

4. **会话与消息流 — 当前阻塞**

   当前运行时持续出现 `Maximum update depth exceeded`，本次截取的 200 条错误日志全部为该错误。源码中的反馈 hook 在依赖 `remote` 或 `sessionId` 变化时重建 Map 并写状态；当前 Remote 引用很可能在渲染间不稳定，形成循环。应优先复用官方的 Session 级反馈 Controller，或把 Remote 解析稳定到 Runtime 生命周期，再让 effect 只随稳定服务和 Session 变化。

   这也是为什么 122 项单元测试全部通过仍不足以判定会话页健康：缺少一次真实挂载的浏览器级回归检查。

   代码：[Transcript.tsx](../../apps/dcode-ui/src/client/chat/Transcript.tsx)

5. **右侧开发上下文 — 能力强但过密**

   Git 变更、Diff、目标/计划、工具详情和命令输出是 DCode 最清晰的优势。290 个变更时，树列表出现截断、零增删统计和高密度视觉噪声；虽然已区分 staged/unstaged，但 UI 没有 stage/unstage 操作，提交入口因此不是完整闭环。分支菜单也是只读。

   “终端”目前只是从会话账本聚合的命令输出，不是交互式终端。若暂不做真实终端，应改名“命令输出”，提供跳回原工具调用、复制、重跑和按命令折叠。

   证据：[DCode 工作区与 Git](05-dcode-workspace.png)

6. **设置与模型提供商 — 需改进**

   设置页结构清楚，编辑提供商也足够直接。当前 DeepSeek 提供商同时出现绿色状态点与“缺少 API Key”的可访问名称：视觉语义与真实状态冲突。代码把 `row.active` 也作为绿色条件，导致“已加载配置”被误表达成“可用”。

   应统一为三态：未配置、已就绪、连接错误；只有凭据存在且探测成功才使用绿色。编辑区保留一个退出动作，并让空 Key 时的保存按钮明确说明结果。

   证据：[模型提供商](09-dcode-settings-models.png)、[编辑提供商](10-dcode-provider-edit.png)

7. **插件市场与配置 — 功能领先、发现体验高风险**

   安装前审阅门槛设计很好：明确列出 DSH 契约、平台、外部 Runtime、联网、激活、已知问题和验证状态，并且只有二次确认才安装。

   但市场把 GitHub `dsh-plugin` 话题的 12,629 个结果直接按卡片平铺，首屏出现 Harness 本体、简历工具、图床等大量非插件或未验证项目。“Portable 未验证”成为几乎所有条目的默认徽标，用户无法建立有效判断。

   默认页应只展示“已验证/精选/与当前平台兼容”的目录；通用 GitHub 结果放入“探索全部”，并提供兼容性、最近维护、风险、类别和来源筛选。星标只能是次级排序信号。

   设置中的 179 个运行时模块不应叫“已安装插件”。当前名称还会把内部 phase `active` 与模块 ID 拼在一起并重复“已停用”。应拆成“用户安装的扩展”和“运行时模块（高级）”，默认隐藏系统模块，提供人类可读名称、说明、依赖和重启状态。

   证据：[插件市场](13-dcode-plugins.png)、[安装审阅](14-dcode-plugin-review.png)、[插件配置](11-dcode-plugin-config.png)、[运行时插件清单](12-dcode-installed-plugins.png)

8. **学习资料库 — 有差异化潜力**

   学习模式视觉清楚，概念、问题、材料三种入口也易懂。现在它更像独立应用；要成为工作台优势，应把学习结果带回任务上下文，例如“从当前仓库生成概念卡”“把一次 Agent 解释保存为笔记”“从当前错误创建学习路线”。

   证据：[学习模式](15-dcode-learning.png)

9. **命令面板与窄屏 — 强**

   命令面板已能统一操作、任务、文件和配置，并具备良好的对话框、组合框和列表语义。900px 下右栏自动收起，核心输入仍可用。这两项都应继续作为 DCode 的主交互骨架。

   证据：[命令面板](17-dcode-command-palette.png)、[窄桌面](16-dcode-narrow.png)

## 优先级路线

### P0：先恢复稳定和可信度（1–3 天）

1. 修复 Transcript 反馈 hook 的重渲染循环；增加一次挂载空会话并断言只加载一次反馈的浏览器回归测试。
2. 修复提供商状态：绿色只代表真正可用；无 Key 为琥珀色“未配置”，连接失败为红色。
3. 给空状态加入非阻塞“就绪清单”：工作区、模型、API Key。发送时缺失再就地阻止，并给单一 CTA；不要复制官方的重复模态框。
4. 修复插件运行时清单的 `active/disabled` 拼接与重复状态，先把系统模块收进高级模式。
5. 插件市场默认改为精选/验证目录；通用 Topic 搜索降级为探索页。

### P1：把功能收束为开发驾驶舱（1–2 周）

1. 空任务默认关闭右栏；发生文件修改、问题或长任务后，先出现紧凑状态条，再由用户展开对应面板。
2. 统一顶部与输入区的工作区/模式信息；相同值不重复，只有临时覆盖时才在输入区出现。
3. Git 补齐 stage/unstage、按组操作、搜索、单目录折叠、零统计隐藏和大列表虚拟化；提交前显示 staged 摘要。
4. 模型选择器增加能力、上下文、视觉、实验/稳定、速度/费用与凭据状态；给出“推荐用于当前任务”。
5. 设置页增加搜索、语义标题、统一图标、未保存状态和底部固定操作区；清除中文界面的 `All`、`Modified`、`Untracked`、`Collapse`、`live`、`Workspace files` 等残留。
6. 将“终端”改名“命令输出”，或真正补齐交互终端；不要让名称承诺超过实现。

### P2：形成官方难以复制的差异化（2–6 周）

1. 长对话导航：保留现有回合轨道、书签、反馈和分支，再增加分支树、分支比较、压缩前预览和上下文消耗预测。
2. 任务驾驶舱：用一条可展开的状态带汇总目标、计划进度、上下文、改动文件、正在运行的工具和阻塞项。
3. Agent 活动中心：后台任务、命令输出、变更、失败与重试统一成时间线；每个结果能跳回消息、文件或 Diff。
4. 插件工作区配置：按工作区保存启用集合、权限和版本锁定，支持“一键安全配置”。
5. 学习与开发闭环：仓库概念图、错误回顾、会话总结和知识卡片从当前任务直接生成并可再次引用。
6. 使用统计从展示升级为决策：按工作区/任务/模型显示 tokens、时长、失败率与上下文浪费，给出可执行建议。

## 推荐的信息架构

| 区域 | 只承担什么 |
| --- | --- |
| 左栏 | 工作区、任务、全局入口 |
| 中央 | 对话、审批、问题、当前任务行动 |
| 顶部状态带 | 当前范围、分支、任务状态、少量告警 |
| 右侧按需面板 | Git/Diff、目标/计划、命令输出、工具详情 |
| 输入区 | 本次提交的内容、上下文覆盖、权限、模型 |

核心原则是“能力随任务出现”，而不是“能力永远占据屏幕”。

## 视觉与可访问性收尾

- 保留当前黑灰体系与紧凑圆角，但提高次级文本和边框的层级差，避免所有卡片都处于同一视觉重量。
- 用统一图标替换设置中的 emoji；市场卡片减少满宽大卡，精选区可用两列，搜索结果使用紧凑列表。
- 设置区标题应使用真实 heading；插件清单的可访问名称应只读出“名称、状态、展开状态”，不要拼接内部 phase。
- `@` 补全需要为当前选项补齐 `aria-activedescendant` 和展开状态；主要流程补全清晰焦点环、Esc 返回层级和状态 live region。
- 本次没有跑屏幕阅读器、完整键盘巡检或颜色对比计算，因此这些属于确认到的语义风险，不是完整 WCAG 结论。

## 建议验收指标

- 新用户从启动到可发送第一条提示不超过 60 秒，并且不需要查文档。
- 空会话静置与切换 30 次任务时无控制台错误、无重复反馈请求。
- 300 个 Git 变更和 200 个运行时模块时，滚动、筛选和展开保持即时响应。
- 用户能在 5 秒内判断模型/插件是“未配置、可用、错误还是待重启”。
- 键盘可完成：新建任务、切换任务、选模型、发送、打开 Diff、切换右栏和关闭弹层。

## 证据限制

- 未使用真实 API Key，因此真实生成、长转录、图片请求、工具调用、消息评分和分支没有完整跑通。
- 原生目录选择器不在网页截图层内，本次只验证了工作区已创建后的状态。
- 本次结论反映 2026-08-30 的当前工作树；仓库存在用户尚未提交的修改，未对其做回退或覆盖。
