## 测试套件简化优化诊断

对全仓测试做了审计，结论：问题不是"测试太多"，而是结构性浪费——成本付了、收益没拿到。

### 量化基线
- 118 个测试文件，19,869 行
- 分布：interactive-learning 11,764 / scripts 2,158 / desktop-node 1,649 /
  runtime 1,359 / dcode-ui 875 / vision-bridge 858 / desktop-Pester 657 / packages 346
- 耗时实测：packaging 38s、runtime 23s、vision 17s、Pester 93s

### 已确认问题（按严重度）
1. **CI 覆盖缺口**：`.github/workflows/verify.yml` 只跑 packaging / learning /
   runtime / install-unix.sh / readme:check。根 `pnpm test` 串的 7 个子集里，
   desktop:test、desktop:updater:test、dcode:test、vision:test 共 43 文件约
   4,039 行在 CI 上从未执行。vision 实测 17s 纯 vitest，Linux 完全兼容，可零成本恢复。
2. **副作用污染 + 顺序耦合**：`version-consistency.test.ts` 串跑失败、单跑通过。
   根因是 `client-manifest-bridge.test.ts` 真实 `rmSync`/`writeFileSync` 到
   `vendor/deepseek-harness/packages/portable`；`dcode-ui` 的 test 跑
   `tsc -b && tsdown` 重写 `lib/`；learning 的 `test:package` 跑 build。
3. **时序敏感 flaky**：`runtime-supervisor.test.cjs` 的两个 timeout 用例
   （#44 / #45）在完整套件里失败、单文件跑通过；`process-tree.test.cjs`
   同样受负载影响（依赖 taskkill）。
4. **硬编码哈希快照门**：`scripts/release/version-consistency.test.ts` 用两个
   sha256 常量断言"和上次一样"而非"正确"，错误信息直接教人刷新，门已失效。
5. **测试发现靠手工枚举**：根 package.json 硬编码 21 个路径，apps/desktop
   硬编码 18 个 test + 21 个 `node --check`，apps/runtime 硬编码 10 个。
6. **巨型 spec**：broker.spec.ts 1,641 行含 4 个 describe，其中
   "session-scoped learner-state Host wiring" 属 learner-state 职责；
   learner-state.spec.ts 1,552 行。

### 已验证可用的技术前提
- Node v22.22.2 与 tsx 均支持 glob：`node --test 'src/*.test.cjs'`、
  `tsx --test 'scripts/release/*.test.ts'` 实测通过。

## 独立问题三：Win32 目录选择器失败「无法打开文件夹」（已修，待重启生效）

**现象**：官方 UI 弹窗「无法打开文件夹」→
`directory picker failed: directory picker failed: win32 folder dialog worker exited before reporting a result`。

**错误链**（三层包装，定位时别被重复前缀误导）：
1. `win32-dialog.ts` worker `exit` 事件 → `win32 folder dialog worker exited before reporting a result`
2. `workspace-controller/directory-picker.ts:58` `cancellableFailure` → 加一层 `directory picker failed: `
3. `ui-workspace` 客户端 `navigation.ts:142` → 再加一层，故消息里出现两次前缀

**UI 归属**：标题「无法打开文件夹」来自 `@deepseek-ai/dsh-client-ui-workspace`
（`folderError.title`），**不是** dcode-ui。dcode-ui 的 `Workbench.openWorkspace` 在
`.catch` 里 `setBrowsing(true)` 会降级到内置浏览器；**官方 UI 没有降级路径**，
只会重开同一个失败的 native 流程 → 用户被彻底卡死。这是"无法开始工作"的直接原因。

**排查结论：静态无法复现**。逐项验证均正常——
`--no-asar` 打包（真实文件）、worker.cjs 存在且补丁契约一致、
koffi 二进制在 `@koromix/koffi-win32-x64/win32_x64/koffi.node`、
`CoInitializeEx` 返回 0、路径解析正确、
端到端（Electron-as-Node + pipe stdio 父进程 → runtime → worker）成功弹出对话框。
→ 判定为时序/竞态，不再继续猜，转为提升可诊断性 + 提供逃生舱。

**已修（3 个补丁文件，均通过测试与 tsc）**：
1. `patches/dsh-host-directory-picker-native-index.js`
   - `stdio` 的 stderr 由 `inherit` 改 `pipe` 并累积（`worker.workerStderr()`），
     同时仍转发到 `process.stderr` 保留原有日志可见性
   - `exit` 处理器带上 `code` / `signal` / `stderr`
   - 实测：崩溃时从干巴巴一句变成 `... (code=3, signal=null, stderr=BOOM: ...)`；
     koffi 缺失时能直接报 `Cannot find package 'koffi'`
2. `scripts/build/runtime-patches.ts` 的 `patchDirectoryPickerWorker`
   - worker 顶部两个守卫（`DSH_DIALOG_TITLE` / `process.send`）原本是
     async IIFE **之外**的顶层 throw → 未捕获异常直接杀死进程、发不出 IPC。
     改为 `failStartup()` 先 IPC 上报再退出，并镜像到 stderr
   - 新增 `uncaughtException` / `unhandledRejection` 兜底
3. `patches/dsh-host-directory-picker-auto-index.js`
   - 新增 `DSH_DIRECTORY_PICKER_BACKEND=browse|native` 环境变量覆盖（逃生舱）
   - **顺带修掉一个真实设计缺陷**：该函数开头是
     `if (source.includes('dshIsWsl')) return source` 的整体短路守卫，
     而 vendor 与 apps/runtime 的副本早已被就地打过补丁 →
     任何**新增** hunk 都会被永久静默跳过。已改为每个 hunk 用自己的 marker 独立判重。

**逃生舱用法**：设置环境变量 `DSH_DIRECTORY_PICKER_BACKEND=browse` 后启动，
强制走内置目录浏览器，绕开 native/COM 整条链路。

**生效方式**：热修复脚本
`pnpm exec tsx .workbuddy/probe/apply-patch-local.ts "<...>/runtime/resources/app"`
（幂等，已实测）。需**先关闭正在运行的程序**（排查时有 5 个 `DeepSeek Harness.exe` 进程）。

**环境备注**：`wmic` 被安全策略禁用；PowerShell 工具输出未被捕获；
Git Bash 传 Windows 路径会被 MSYS 转成 `\c\Users\...`，给 Windows 程序传参要用 `C:/...` 形式。

### ★ 本轮推翻「时序/竞态」结论：已确定性复现 + 根因修复（晚 22:20 后）

真实根因：**koffi 的 `koffi.view()` 在 Electron 43.4.0 内置 Node 24.18.1（V8 15.0-electron, ABI 148）下致命崩溃**——
`FATAL ERROR: Error::New napi_get_last_error_info`（SIGABRT/134），**对有效指针也崩**。
触发点：用户真正**选中文件夹**后 `resultPath() → readUtf16()`（worker.cjs:22）。
之前的端到端测试通过是因为**取消路径不经过 readUtf16**（worker.cjs:179 取消直接 return null）——
弹窗成功 ≠ 选目录成功，这是当时误判为竞态的原因。

复现矩阵：Electron 43.4.0 + koffi 3.1.6/3.1.5 均崩（排除版本漂移）；独立 Node 22.22.2 / 24.16.0 均正常。
→ 问题特定于 Electron 43 定制构建，与 koffi 小版本无关。

已验证修复：readUtf16 改用 `lstrlenW + RtlMoveMemory + Buffer.toString`（绕过 koffi.view），
Electron 43 下实测通过；顺带消除原实现固定过量读 64KB 的隐患。
补丁：`patches/dsh-host-directory-picker-native-worker.js`（**待登记 patches/manifest.yml 的
directory-picker-electron-ipc files**，随后重打包或热应用）。
报告：`output/DSH-目录选择器报错定位分析-20260829.md`；复现/验证脚本在 `output/koffi-*.cjs`。

附带发现：① lockfile 锁 koffi 3.1.5、运行时实装 3.1.6（node_modules 未按 lockfile 安装）；
② 报错①（打开工作区 Failed to fetch）与 koffi 崩溃无关：网关 127.0.0.1:6488 存活（401 鉴权响应），
"Failed to fetch" 是浏览器网络层失败（连接拒绝/origin 回退 http://dsh.internal），
最可能是启动时序或对话框窗口 origin 异常，待 F12 取证（location.origin + net::ERR_*）。
